rainy — implementation notes

1. Current status

Hong Kong district rainy-day lookup is live as a Cloudflare Worker over D1. The Mac/Actions job scrapes HKO monthly; the Worker answers GET /rainy?district=&dates= with Authorization: Bearer or X-API-Key at https://hk-rainy-day.ngcheukhim.workers.dev.

  • Source: HKO / DATA.GOV.HK daily total rainfall (25 official stations).
  • Trace / 微量 = 0 mm. Rainy only if district rainfall ≥ 0.2 mm.
  • Wan Chai + Southern → The Peak (VP1). Kwun Tong → Kai Tak (SE).
  • Missing HKO values → unknown (null), not dry. Rainy if that day’s district rainfall ≥ 0.2 mm.
  • Excel / old CSVs are analysis only and are not loaded by the app.

2. Decisions

  • One table: rainy_day_lookup (~17.5k rows). Query is one indexed SELECT.
  • Scrape on Mac or GitHub Actions. Not inside a free Worker (10 ms CPU, 50 subrequests).
  • No VPS. Monthly job is a few Linux minutes.
  • This feed is monthly QC climate data. It will not give “yesterday morning.”
  • Public GitHub repo for unlimited Actions minutes. Keep workflow_dispatch. Secret: CLOUDFLARE_API_TOKEN.
  • API covers 18 District Councils + Lantau Island split (19 keys).
  • Worker deploys from deploy-worker.yml when Worker sources change. Rainfall D1 updates stay on update-rainfall.yml.
  • Header-only API key. Query-string ?key= is rejected. CORS is *, so this key is for a backend caller, not a public web app.
  • Weekly job stores HKO Last-Modified/ETag fingerprints and rebuilds only when they change. Monthly job on the 10th always rebuilds.
  • Python and Worker tests run on every push/PR and before a D1 import.
